**Part 1: Playwright Fixture Infrastructure (e2e/conftest.py)**

Create pytest fixtures for Playwright-based E2E tests:
- `browser_context`: Isolated Chromium browser context with persistent storage disabled (no cross-test cache)
- `app_server`: Spawn isolated Uvicorn subprocess with temp SQLite database (`sqlite:///e2e-{timestamp}.db`), run migrations via Alembic, seed P-1042 fixture data and three users (admin, doctor, sarah)
- `auth_headers`: Factory fixture to generate Bearer tokens for each role (admin, doctor, nurse)
- `base_url`: Return subprocess Uvicorn host/port (localhost:8001)
- `cleanup`: finally block terminates Uvicorn child and deletes temp database file

Import patterns from backend/tests/conftest.py: use make_client pattern, clock injection (fixed datetime), session_factory, and secret preflight.

**Part 2: Full Journey E2E Test (e2e/test_tracer_full_journey.py)**

Write ONE comprehensive end-to-end test that proves all ROADMAP success criteria in one happy path. Test must run in < 2 minutes and exercise:

1. **Admin Setup (0:00-0:10)**
   - Admin logs in via `/api/v1/auth/login` (email: "admin@acuitynet", password seeded)
   - Receives 200 + JWT access_token
   - Assert response contains token format and expiry

2. **Doctor Pre-Flight (0:10-0:20)**
   - Doctor logs in and navigates to P-1042's monitoring page
   - Assert page loads without 403 or 404
   - Assert UI shows patient ID "P-1042", bed assignment
   - Assert "Simulated ICU" or "Research Prototype" label visible
   - Assert current vitals displayed (SpO2, HR, RR, BP, Temp, timestamp)

3. **Synthetic Vitals Deterioration (0:20-0:35)**
   - Admin advances vital ticks 0→1→2→3→4 via `/api/v1/patients/P-1042/vitals/advance`
   - Each tick returns 200 + new vital snapshot
   - Assert vitals change deterministically with each tick (HR increases, SpO2 decreases)
   - Assert "Simulated" or "Synthetic" provenance visible in API response

4. **Prediction and Fallback Label (0:35-0:45)**
   - Doctor fetches P-1042 prediction via GET `/api/v1/patients/P-1042/prediction`
   - Assert response includes: risk_score, risk_level, predicted_event, probability, horizon, source_kind
   - If ML provider is unavailable, assert source_kind == "deterministic_fallback" and fallback_reason is populated
   - Assert response does not include clinical diagnosis or treatment language

5. **Alert Generation at Threshold (0:45-0:55)**
   - After tick 3 or 4, crossing the critical threshold triggers alert creation
   - Doctor refreshes monitoring page or polls GET `/api/v1/patients/P-1042/alert`
   - Assert 200 + alert object with state="generated", priority (high/critical), alert_id, created_at, provenance
   - Assert alert contains prediction evidence link and patient risk summary
   - Assert synthetic provenance visible in alert rendering

6. **Historian Context Retrieval (0:55-1:05)**
   - Doctor navigates to historian page and fetches GET `/api/v1/patients/P-1042/historian`
   - Assert 200 + historian object with:
     * Demographics (name, DOB, admission date, bed)
     * Diagnoses list (populated from fixture)
     * Medications list
     * Labs (glucose, potassium, etc. from fixture)
     * Previous ICU events (historical incidents from fixture)
     * Baseline risk (prior probability) and contextual risk (current delta)
     * Rule explanations (each rule name, factor, delta) labeled as "prototype rules"
   - Assert response does not claim validated clinical weighting

7. **Dispatch Evaluation and Ranking (1:05-1:15)**
   - Doctor POSTs `/api/v1/patients/P-1042/dispatch/evaluation` with alert_id
   - Assert 200 + evaluation object with:
     * Ranked candidates array (Sarah should be top candidate)
     * Score breakdowns: availability, proximity, workload, acuity (no model_score component)
     * Exclusion reasons for any unavailable nurses (empty in nominal case)
     * Outcome: "recommendation_available"
   - Assert recommendation does not claim autonomous decision

8. **Human Confirmation of Dispatch (1:15-1:25)**
   - Admin POSTs `/api/v1/patients/P-1042/dispatch/confirm` with evaluation_id and confirmed_nurse_id="U-SARAH"
   - Assert 200 + assignment object created
   - Assert alert state transitions to "assigned" with assignment_id
   - Assert audit event recorded: {actor: "U-ADMIN", action: "confirm_dispatch", outcome: "confirmed"}
   - Assert confirmation reason captured (e.g., "Highest availability and proximity")

9. **Nurse Receives and Acknowledges Assignment (1:25-1:35)**
   - Sarah (nurse) logs in and navigates to her alert page
   - Assert page shows assigned P-1042 alert with priority badge, risk score, bed info
   - Sarah POSTs `/api/v1/patients/P-1042/alert/acknowledge` with assignment_id
   - Assert 200 + alert state transitions to "acknowledged"
   - Assert audit event recorded: {actor: "U-SARAH", action: "acknowledge", timestamp, outcome: "acknowledged"}

10. **Nurse Records Response (1:35-1:45)**
   - Sarah POSTs `/api/v1/patients/P-1042/alert/respond` with {assignment_id, response_note: "Patient stable, vitals improving, monitoring continued"}
   - Assert 200 + alert state transitions to "responded"
   - Assert response_note persisted
   - Assert audit event recorded: {actor: "U-SARAH", action: "respond", timestamp, outcome: "responded"}

11. **Nurse Resolves Alert (1:45-1:55)**
   - Sarah POSTs `/api/v1/patients/P-1042/alert/resolve` with assignment_id
   - Assert 200 + alert state transitions to "resolved"
   - Assert resolved_at timestamp populated
   - Assert audit event recorded: {actor: "U-SARAH", action: "resolve", timestamp, outcome: "resolved"}

12. **Audit Trail Reconstruction (1:55-2:05)**
   - Admin fetches GET `/api/v1/patients/P-1042/audit`
   - Assert 200 + audit events array with ≥12 events:
     * Configuration change (threshold update)
     * Vital advance ticks (3-4 events)
     * Alert creation
     * Dispatch evaluation
     * Dispatch confirmation
     * Nurse acknowledgement
     * Nurse response
     * Nurse resolution
     * Any denials or errors
   - Assert events are ordered by timestamp (ascending)
   - Assert event details do not leak passwords or bearer tokens
   - Assert sensitive data (PHI) is minimal and role-scoped

13. **Operational State Visibility (2:05-2:10)**
   - Inject stale condition: Doctor's last API fetch was >15 min ago
   - Doctor refreshes alert
   - Assert UI shows "Stale" badge or "Last updated 15+ min ago" warning
   - Assert "Refresh" button available and usable
   - Assert data remains visible (not hidden due to staleness)

14. **REST Recovery After WebSocket Disconnect (2:10-2:15)**
   - If WebSocket was used for real-time updates, simulate client-side disconnect (page.evaluate("window.socket?.close()"))
   - Assert page shows "Offline" or "Reconnecting..." state
   - Click manual "Refresh" or wait for automatic reconnect
   - Assert page fetches latest state via REST
   - Assert UI returns to "Online" state with updated data

**Test Implementation Notes:**
- Use Playwright's `page.goto()`, `page.fill()`, `page.click()`, `page.wait_for_selector()` for navigation
- Mock browser network delay minimally (prefer 0-100ms for determinism)
- Capture screenshots at each major step for debugging
- Use `page.on("response")` to verify HTTP status codes and response contracts
- Assert JSON response structure using jsonschema or simple dict key checks
- No interactive waits or timeouts > 3 seconds (test must complete in < 2:15)
- Use injected clock (fixed datetime) to avoid timing flakiness
- Cleanup: browser_context.close() in fixture

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test code → Subprocess Uvicorn | Test harness launches isolated backend; temp database is ephemeral |
| Browser automation → REST/WebSocket APIs | Playwright client simulates real user interaction; no mocked responses |
| Audit trail → Persistent evidence | All lifecycle actions recorded with actor, timestamp, and outcome |
| Synthetic data → UI rendering | Provenance labels distinguish simulated from clinical |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Spoofing | JWT session | medium | mitigate | Test uses seeded credentials; real JWT validation on each API call; invalid token returns 401 |
| T-05-02 | Tampering | Audit trail | high | mitigate | Insert audit events only via authenticated POST endpoints; verify ordering by timestamp and event ID |
| T-05-03 | Repudiation | Lifecycle mutations | high | mitigate | Assert audit detail captures actor, timestamp, state transition, and outcome for every mutation |
| T-05-04 | Information Disclosure | Browser screenshot/logs | high | mitigate | Cleanup temp database after test; never print bearer tokens; redact sensitive fields in error messages |
| T-05-05 | Information Disclosure | Stale data presentation | medium | mitigate | Assert stale badge visible but data remains readable; no PHI hidden due to staleness |
| T-05-06 | Denial of Service | No-candidate state | medium | mitigate | Assert alert stays "generated" when no eligible nurses exist; no retry loop without admin intervention |
| T-05-07 | Elevation of Privilege | Role bypass | high | mitigate | Assert unassigned nurse cannot read/mutate P-1042 alert; API returns 403 with generic reason |
| T-05-SC | Tampering | package installs | low | accept | No new npm/pip packages in tracer; Playwright and pytest already vetted and pinned |
